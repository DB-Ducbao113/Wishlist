# Dream Vault V16.1 - F5 Savings & Product Intelligence

Branch `feature/motion-auth-reset`, PR #1 -> `develop`. Baseline F4 HEAD
`f22401d`. Budget $0. **No Production action of any kind was taken**: nothing was
merged, nothing was tagged (no F5 tag exists), nothing was deployed,
`ui-v16.0.0 -> 562a62f` was not moved, and the Firestore rules and the Cloudflare
Worker were not touched.

F5 adds the one thing the app was still missing to be useful *before* a purchase:
the user can say what an item costs them in effort, put money aside for it, and
see where they stand. It is built on the F2 purchase-fields pattern and the F3
dashboard, and it is deliberately deterministic - no model, no score, no
recommendation that pretends to know what the user can afford.

## 1. What was built

### 1.1 F5.1 - the data model, and how it stays compatible

Two optional fields on an item: `savingGoal` (what the user is aiming at) and
`savedAmount` (what the user says they have put aside). They are *optional in the
strict sense*: absent is a real state, and absent is what they stay.

The shape helpers are copied from the F2 purchase-fields pattern, because that
pattern already survived an F2 review, is already covered by 168 assertions and
already knows how to keep "no value" distinct from "zero":

* `validSavingGoal(v)` - a finite, safe integer `> 0`, or `null`;
* `validSavedAmount(v)` - a finite, safe integer `>= 0`, or `null`;
* `setSavingsFields(it, {savingGoal, savedAmount})` - writes a key only when the
  value is real, and **deletes** the key when it is not;
* `clearSavingsFields(it)` - removes both;
* readers that never trust anything: `readSavingGoal`, `readSavedAmount`,
  `savedOf`, `hasSavingGoal`, `savingsReached`, `savingsRemaining`,
  `savingsProgress`;
* `computeSavings(list)` - one aggregate over unpurchased rows.

The rules that matter, and where each one is enforced:

| Rule | Where |
| --- | --- |
| never default "saved" to the list price | `setSavingsFields` only ever writes a user-supplied value; nothing reads `it.price` |
| never write a fake value | an empty field deletes the key, it does not write `0` |
| never silently overwrite old data | `normalizeItem` rewrites a row's savings **only** from the row's own values; a row without them is left without them |
| keep old rows working | an absent field is handled at every read site (`savedOf` -> `0`, `savingGoal` -> `null`) |
| reject negative / NaN / Infinity / junk | `validSavingGoal` / `validSavedAmount`, and again in `normalizeItem` |
| `savedAmount > savingGoal` is **not** clamped | `savingsReached` is `saved >= goal`; the bar caps at 100 % but the stored number is untouched (F5-2-20) |
| price, goal and actual paid stay three different things | the goal and the amount paid live in separate sections, are written by separate helpers and are rendered in separate lines |
| never auto-deduct from another item | nothing writes on read; the only writers are the form, the Quick View and reset |
| no new Firebase collection | the two fields ride on the item document |

Savings are **independent of the purchase status**. That is the one place F5
deliberately diverges from the F2 purchase fields: `normalizeItem` strips
purchase fields from a row that is no longer purchased, but it **keeps** the
savings fields on a purchased row, because buying the thing does not un-save the
money (F5-1-12). `computeSavings()` filters purchased rows out of the *aggregate*,
not out of the data.

`computeMetrics()` (F3) was not touched. Savings got their own function so the F2
and F3 key-set assertions in `v16_2`/`v16_3` cannot shift underfoot.

### 1.2 F5.2 - the goal, set and edited in two places

**Add / Edit form.** A new "Mục tiêu tiết kiệm" section with two optional
fields and a live preview. The preview updates on input, not on save. It hides
itself when there is nothing true to show, so there is no `0/0` bar and no
`-50.000 ₫` remainder: a goal of `0`, a blank goal or a negative goal simply
means "no goal yet". When the goal is met the bar caps at 100 % and the copy
switches to "Đã đạt mục tiêu", with the amount over the goal kept as recorded.

Writing `0` in the goal field is not a validation error - it means the same as
leaving it blank, and neither the goal nor the recorded amount is destroyed. A
negative goal *is* refused, in Vietnamese, with focus put on the offending field,
and neither field is written (F5-2-09, F5-2-10).

**Quick View.** The same two fields, edited **in place** - no stacked dialog, so
the savings decision is made on the item, where the user is already looking. It
shows the amount still missing until the goal is met, then says the goal is
reached *and that the item is still not bought*, so "savings reached" can never
be misread as "purchased" (F5-2-19).

**Reset** asks once, in Vietnamese, naming the item:

> `Xóa mục tiêu tiết kiệm của "<tên món>"? Số tiền đã để dành cũng sẽ bị xóa.`

Dismissing it deletes nothing (F5-2-23); accepting it removes both keys and the
block falls back to its empty copy (F5-2-24). The form is the second, ordinary
path: clearing both fields and pressing Lưu removes the keys too. The form does
**not** ask for a second confirmation - clearing a field the user typed is
already an explicit act, and the destructive-shaped operation (reset) is the one
that asks.

### 1.3 F5.3 - the savings overview, and how a figure becomes a filter

Four figures in the Light Lavender language the dashboard already speaks:

| Row | Value | Meaning |
| --- | --- | --- |
| Mục tiêu đang theo dõi | the sum of the goals + `N món có mục tiêu` | how many goals, and how much they add up to |
| Đã tích lũy | the sum of the recorded amounts | what the user says they have put aside |
| Còn thiếu | `max(0, goals - saved)` per item, summed | the honest remainder |
| Đủ tiền, chưa mua | a count | reached but not bought - the next decision |

The aggregate progress bar is the only "progress" thing F5 adds, and it is the
same horizontal `role="progressbar"` shape F3 installed. **No progress ring was
added** - that refusal is still binding, and `#dvProgress` is still the only
progressbar on the dashboard.

Only valid goals on unpurchased rows are counted, each item counts once, an
over-saved item does not cancel another item's gap (F5-1-16), and a purchased row
is excluded from every figure (F5-3-05). When nothing qualifies, the whole card
is removed rather than left as a shell of zeros (F5-3-06, F5-3-07).

Every figure is a real `<button>` with a full `aria-label`, and clicking one
**only sets filters the toolbar already has**: a new savings facet in the F4.4
filter panel (`#fSavings`, one `<select>` with `"" | goal | saving | short |
ready`) plus the "Chưa mua" quick tab. So the set that lands is exactly the set
that was counted (F5-3-09, F5-3-10, F5-3-11), the other facets and the search box
are reset on the way (F5-3-12), and one "Xóa bộ lọc" clears the new facet with
everything else (F5-3-14).

The facet is orthogonal to status by design - it asks a question about the item's
own savings fields and nothing else, so it is still true for a purchased row; the
dashboard rows pair it with the "Chưa mua" tab to make the landed set match.

`#fSavings` *is* a facet in the existing panel rather than a fourth quick tab,
because `v16_2-f2-check.js:1417` asserts the quick-tab row's geometry at 320 /
390 / 430 px, and `applyDashboardFilter` is already a facet-patch contract
(`{ status?, priority?, category?, savings?, tab? }`).

### 1.4 F5.4 - what to look at next, deterministically

A short list of unpurchased items, ordered by rules, not by a model:

| Rank | Rule | Reason shown |
| --- | --- | --- |
| 1 | priority `high` | `Ưu tiên cao` |
| 2 | savings goal reached | `Đã đạt mục tiêu tiết kiệm` |
| 3 | has a goal, still short | `Còn thiếu <số tiền> ₫ tới mục tiêu` |
| 4 | anything else unpurchased | `Chưa mua` |

Ties break on `createdAt` ascending, then `id` ascending, so the order is stable
and independent of the array order (F5-4-07). The list is capped at
`DV_INSIGHT_LIMIT = 4`, so the dashboard cannot grow into a second collection
listing (F5-4-08). A purchased item is never suggested (F5-4-06).

Every row carries its reason, and the visible affordance is an explicit
**"Xem món"**; the row is one `<button>` and the `aria-label` repeats the action,
the item, the reason and the recorded price, so a screen reader gets the reason
too instead of losing it to the label (F5-4-15). "Xem món" opens the Quick View
for that item and changes nothing - no status, no purchase, no count (F5-4-10).

The wording never claims financial capability. There is no sentence of the form
"bạn có thể mua" or "nên mua"; the reasons are facts about the data (F5-4-11).

### 1.5 F5.5 - UX, tokens, and what was deliberately not added

* The **Light Lavender palette is unchanged** (`#F8F6FF`, `#FFFFFF`, `#F3EFFF`,
  `#6850BC`, `#A88BF7`, `#19152C`) and the new stylesheet is built from the
  existing `--dv-*` tokens - `--dv-text-caption`, `--dv-gap-*`, `--dv-accent`,
  `--dv-ink`. No new token, no second design language, no new design system.
* The existing components are reused: the dashboard card, `.dv-progress`'s bar
  geometry, `.dv-priority`'s row shape, `product-dialog__section` /
  `product-dialog__row` / `product-dialog__section-hint` in the form,
  `.quick-view__btn--glass/--ghost` in the Quick View.
* **No chart library and no new runtime dependency.** The whole feature is inline
  in `wishlist.html` plus one stylesheet (F5-5-04, F5-5-05).
* No overflow at 320 / 375 / 390 / 430 px, and none at 1440 (F5-5-01,
  `f5-desktop-dashboard.png`).
* Both widgets hide themselves when they have nothing to say, and the row uses
  `repeat(auto-fit, minmax(min(100%, 300px), 1fr))`, so a lone visible widget
  spans the row instead of leaving an empty column (F5-5-03) - without needing
  `:has()`.
* The F4 surfaces are intact: the card `...` menu, the Quick View, the phone
  filter disclosure and the dashboard quick actions all still work
  (F5-5-06 .. F5-5-08, and the whole F4 gate below).
* Motion is additive and cheap: the same 240 ms `dvNudge` WAAPI nudge F3 uses,
  and a `prefers-reduced-motion: reduce` block that drops it (F5-4-13).

`allow read, write` with no field allowlist, so no rules change is needed. Both
of those are read from the repo, and both are true; neither is the same as having
watched two devices agree.

## 5. Schema compatibility & migration matrix

An item is a plain object in `localStorage` (`wishlist.guest.items`, or
`wishlist.account.<uid>`) and a document in the signed-in user's Firestore
`items` collection. It is read back through `normalizeItem()` on the local path
and read **raw** on the remote path, so every row below is also a claim about a
possibly-hostile remote document.

| Stored shape | What F5 does | Data lost? |
| --- | --- | --- |
| `{}` / legacy row, no savings keys | reads `null` / `0`, renders no progress anywhere, and normalize leaves the row with exactly the key set it arrived with - no savings key appears | **no** |
| `{savingGoal: 1500000}` | goal only; "Đã tích lũy 0 ₫", remaining = the goal, 0 % bar | no |
| `{savedAmount: 400000}` | amount only, **no goal**; no progress rendered (a valid goal `> 0` is required) | no |
| `{savingGoal: 1000000, savedAmount: 400000}` | 40 %, "còn thiếu 600.000 ₫" | no |
| `{savingGoal: 1000000, savedAmount: 1000000}` | reached; bar capped at 100 %; "Đã đạt mục tiêu", still unpurchased | no |
| `{savingGoal: 1000000, savedAmount: 1500000}` | reached; **1500000 stored untouched**, no clamp | no |
| `{savingGoal: 0}` | treated as "no goal" (a zero goal is not a goal); key dropped on the next normalize | the `0` only |
| `{savingGoal: -5}` / `{savedAmount: -1}` | value dropped on normalize | the invalid value only |
| `{savingGoal: "abc"}` / `{savingGoal: NaN}` / `{savingGoal: Infinity}` | `null` at every read site; nothing renders | the invalid value only |
| `{savingGoal: "1500000"}` (numeric string, e.g. from an old hand-edited export) | accepted, stored as the integer | no |
| `{savingGoal: 1e30}` | refused as absurd; dropped | the invalid value only |
| goal set, then the item is marked bought | row keeps both keys; **excluded from the dashboard figures and the shortlist**; re-shown in the Quick View if the purchase is undone | no |
| both keys present, then the user clears both fields and saves | both keys deleted | intentional |
| both keys present, then the user hits reset in the Quick View | both keys deleted, after one Vietnamese confirmation | intentional |
| exported to JSON | the keys are in the export, because the export is `JSON.stringify(items)` | no |
| imported back | the same `normalizeItem` rules run, so a hand-edited import cannot inject a bad value | no |
| remote document with a malformed value | the reader returns `null`/`0`; the value is not written back to the remote by a read | no (the remote value is left as-is until the user saves) |

No migration is needed and none is performed: the fields are additive and
optional, and there is no version bump, no rewrite pass, and no new collection.

### 6.1 Payload, the way Cloudflare serves it

Measured with `f4-payload.js` on byte-exact trees
(`git -c core.autocrlf=false archive` + `tar`), so the raw counts are the bytes
git stores and Cloudflare serves.

| Tree | html raw / gzip | css raw / gzip | js | requests | **TOTAL raw** | **TOTAL gzip** |
| --- | --- | --- | --- | --- | --- | --- |
| F2 baseline `332258f` | 130.4 / 38.5 KB | 283.8 / 79.4 KB (x50) | 0 (ES import) | 51 | 414.3 KB | **117.9 KB** |
| F3 head `93ef2c1` | 162.6 / 47.5 KB | 306.3 / 84.2 KB (x50) | 0 | 51 | 468.8 KB | **131.7 KB** |
| F4 head `f22401d` | 176.6 / 51.5 KB | 318.9 / 87.7 KB (x51) | 0 | 52 | 495.5 KB | **139.2 KB** |
| **F5** | 208.8 / 59.7 KB | 329.8 / 90.6 KB (**x52**) | 0 | **53** | 538.6 KB | **150.3 KB** |

* F4 -> F5: **+43.1 KB raw, +11.1 KB gzip**, of which
  * `wishlist.html` **+32.2 KB raw / +8.2 KB gzip** (807 inserted lines: the
    savings helper block, the form section and its preview, the Quick View block,
    the two dashboard renderers and the facet wiring),
  * **`css/f5-savings-v16.css` is 11.1 KB raw / 3.4 KB gzip**, the entire new
    CSS, and
  * the other 51 stylesheets are byte-identical.
* The single new request is that one stylesheet. `js x0` is correct, not a bug:
  `wishlist-cloud.js` is loaded by an ES `import`.

**A methodology note, because it decides what the Lighthouse numbers below
mean.** The F4 report published F4 as `181.5 KB` html / `506.1 KB` total. That
row came from a working tree with CRLF line endings; `wishlist.html` at
`f22401d` is 180 822 bytes and 4 999 lines, so its CRLF form is
180 822 + 4 999 = **185 821 bytes = 181.5 KB** - the same tree, ±line endings.
The table above normalises all four trees to LF so the F4 -> F5 delta is
apples-to-apples. Anyone re-running this must use the same recipe.

The same line-ending effect explains the other number that gets quoted around
this milestone: `scripts/build-hosting.mjs` copies the **working tree**, so its
`totalBytes` reads `575 092` for the F5 delivery. That figure is a different
question from the `538.6 KB` above, for two reasons: it counts the working tree's
CRLF endings rather than the stored LF bytes, and it counts three files the
payload recipe does not - the ES-imported `wishlist-cloud.js` (11 838 B) and the

56 published files, 54 assets plus 2 platform files, `leakCount 0`, and the
explicit allowlist (`wishlist.html`, `wishlist-cloud.js`, `css`) untouched.

### 6.3 Lighthouse A/B - same flags, both trees

`f5-lighthouse.js`, same flags, same categories, same form factors, same
throttling as the F4 runner, 3 runs per side, medians reported. `transfer` is
Lighthouse's own `total-byte-weight`, which also counts the ES-imported
`wishlist-cloud.js` and so reads slightly above the payload table's request set -
identically on both sides.

**Raw transport** (the static test server sends uncompressed bytes):

point of F4 or better, a11y / BP / SEO within 1 point, CLS 0), with every single
run identical to its twin: F4 desktop 71/71/71, F5 desktop 71/71/71, F4 mobile

What this says, plainly:

* **Compressed - i.e. how the app is actually served - F5 costs nothing.** Every
  category is identical to F4 on both form factors, and F5's LCP is 2 ms and 8 ms
  *faster* than F4's. The +11.1 KB gzip and the two extra renderers do not move
  a single measured metric.
* **The raw-transport mobile drop (74 -> 71) is a transport artifact.** It is
  reproducible (F4 74/74/74 vs F5 71/71/73) because the test server sends the

  every uncompressed byte. Run the same pair with compression and the gap is
  gone, which is the decisive comparison: production does not send those bytes
  raw.
* Desktop is unchanged in both modes (59 raw, 71 compressed), and a11y / BP / SEO
  are pinned at 100, CLS at 0 and TBT at 0 ms in all 24 runs.
* The F4-era drop the F4 report recorded is unchanged and is still the larger
  one: F2 was 61 / 80, F4 is 59 / 74 (raw). F5 did not start that trend.
* The gate therefore reads: **no Lighthouse regression attributable to F5**. The
  raw-transport mobile number is recorded in section 9 as a measurement caveat,
  not as a defect.

## 9. Known gaps, risks and carried-over items

### Blocked, owner-side, exactly as before F5

* The Cloudflare preview build is red until the deployment is retried in the
  dashboard.
* iPhone Google sign-in on the Preview needs the Firebase authorised domain and
  the Google Cloud OAuth redirect URI.
* Two-device image/savings sync cannot be observed here (no iPhone, no real
  Google or Firebase account), so the remote path stays mock-only (section 2.2).
* Production deploy withheld pending release approval.

### New in F5

* **F5-N1 - the raw-transport Lighthouse mobile number is 74 -> 71** (section
  6.3). This is a measurement caveat rather than a finding: the test server sends
  uncompressed bytes, Lighthouse's simulated mobile profile charges for all of
  them, and F5 adds 43.1 KB raw. Under production-style compression the same pair
  is 93 / 93 with F5 marginally faster in LCP, and the gate is PASS on all ten
  checks. Recorded so the number is not silently dropped, and so F6 re-measures
  against F5 rather than against F2.
* **F5-N2 - `wishlist.html` grew 32.2 KB raw.** A single-file app pays for its
  inline JS in the render path. If F6 adds to it, the two obvious levers are
  moving a block of code out into its own `<script>` (a real structural change to
  the single-file pattern, out of F5's scope) or trimming comment volume. Neither
  was done here, and neither is a prerequisite.
* **F5-N3 - the form's clear-to-reset path has no confirmation.** Deliberate (the
  Quick View's reset is the destructive-shaped action and it does confirm), but
  it is a judgement call, not a guarantee, and it is recorded in section 1.2.
* **F5-N4 - the savings facet is a fifth `<select>` in a panel that was designed
  around four.** It fits at every tested width, and the panel is a disclosure on
  phones, but the desktop toolbar is now one control wider than F4's.
* **F5-N5 - a goal on a purchased item is invisible on the dashboard** (it is
  excluded from every figure) and visible only in the Quick View. That is the
  intended F5.3 scope, but a user who saves past a purchase will not see that row
  in the overview.

### Carried over and still open

* P2-3 the misleading `importJson()` comment; P2-4 `#fCategoryFilter` is rebuilt
  on every render; P2-5 `ownedValue` is list price, not paid price.
* F2-N1 the status chip records no `purchasedAt`; F2-N2 no upper bound on
  `paidAmount` beyond finiteness; F2-N3 real-device sync never run; F2-N4 the QA
  harnesses intentionally stay uncommitted in the QA directory.
* F4-N1 `render(50)` costs more than pre-F4 because the card panel must stay
  laid out; F4-N2 the 260 ms hover-reveal is a deliberate trade-off.
* The V4..V15 suites are stale by design and are still not quoted as gates.

## 10. Decision

**GO for F6 (Motion Polish)**, on this branch, with no Production action.

Why:

1. F5.1 - F5.5 are implemented, and the F5 gate is **97 / 97** while every
   declared F1/F2/F3/F4/V16 gate is green at **662 / 662** with zero harness
   edits.
2. The data model is additive, optional and total: no migration, no version bump,
   no new collection, no rules change, and no path that can lose or invent a
   value (section 5).
3. Accessibility, best practices and SEO sit at 100 with CLS 0 and TBT 0 ms on
   both form factors, in both transports.
4. The Lighthouse pair is equal to F4 in every category on both form factors once
   the transport matches production (desktop 71 / 71, mobile 93 / 93, a11y / BP /
   SEO 100, CLS 0, TBT 0 ms), and the only movement anywhere is the
   raw-transport mobile number. F6 should still treat the payload budget as a
   first-class constraint rather than a footnote.

Conditions carried into F6:

* keep the one-stylesheet pattern and add no runtime dependency;
* do not move `ui-v16.0.0`, do not tag F5, do not merge, do not deploy;
* re-measure the same Lighthouse pair after F6's motion work and report the
  mobile number against F5's (not F2's), so the payload trend stays visible.
