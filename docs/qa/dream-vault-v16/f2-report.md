## 1. Bugs fixed (before → after)

Four real defects, all reproduced in the browser before the fix and re-tested
after.

### 1.1 Undo guessed the wrong status

**Before.** `undoPurchased()` computed "the status before `purchased` in the
`STATUSES` list" — i.e. always `ordered`. Marking a `wish` item as purchased
and undoing it therefore left it at **Đã đặt hàng**, which the user never chose.
Reproduced on the F1 tip: seed `status: 'wish'`, click *Đánh dấu đã mua*,
click *Hoàn tác* → `status === 'ordered'`.

**After.** The status the item came from is recorded as `previousStatus` when
the purchase is captured, and undo restores exactly that. Same repro now ends at
`wish`. For rows that predate F2 the fallback is explicit and tested
(`restoreStatusKey()`, M-14/M-15, U-09).

### 1.2 A toast raised while Quick View was open was invisible

**Before.** The toast host only looked at `#dlg`:

```js
const host = $("dlg").open ? $("dlg") : document.body;
```

The Quick View is a `<dialog>` opened with `showModal()`. Anything appended to
`document.body` while it is open is painted **under** the top layer and its
backdrop — so undoing a purchase from the Quick View produced no visible
feedback at all.

**After.** `toastHostElement()` walks the top layer (`#pd` → `#dlg` → `#qv` →
`body`), so the toast is mounted inside whichever dialog is on top. Asserted at
P-30 (parent element is a `DIALOG` while `#pd` is open) and visually in
`img/f2-desktop-purchased-toast.png`.

### 1.3 "Skipped price" was indistinguishable from "cost 0 ₫"

**Before.** Purchase capture did not exist; an item was either purchased or not,
and there was no concept of a recorded price. Once a price field existed, the
obvious implementation (`paidAmount = Number(input) || 0`) would have turned an
empty input into a hard `0`, and the dashboard would have claimed the user had
verified that an item cost nothing.

**After.** An empty amount is stored as **the absence of the field**, never `0`.
A genuine `0` the user typed is stored as `0`. `computeMetrics()` therefore
reports "chưa nhập giá thực tế" for one and 0 ₫ of real spending for the other
(M-05, M-06, P-21, P-22, D-02/D-03).

### 1.4 Metrics were structurally confused

**Before.** `ownedValue` (sum of recorded list prices of owned items) was the
only "spent"-shaped number on the dashboard, and its label invited the reader to
treat it as money that had left the account. Two further facts were not
representable at all: how much was *actually* recorded as paid, and how many
owned items still had no price.

**After.** Five separate figures, three of them shown side by side and never
merged:

| Figure | Meaning | DOM |
| --- | --- | --- |
| Giá trị chưa mua | Σ recorded price of **not**-purchased items | `#sumTotal` |
| Giá trị đã sở hữu | Σ recorded price of purchased items — *not* spending | `#sumSpent` |
| **Chi tiêu thực tế đã ghi nhận** | Σ of **valid `paidAmount` only** | `#dvActualSpent` (new) |
| **Món đã mua chưa nhập giá thực tế** | count of owned items with no `paidAmount` | `#dvUnpriced` (new) |
| Tỷ lệ sở hữu | ownedCount / totalCount | `#dvProgressValue` |

`#dvActualSpent` reads "Chưa ghi nhận" rather than "0 ₫" when nothing has been
priced, so the two states cannot be confused by eye either (D-14, D-16).

## 7. Requirement-by-requirement

### §1 Data model — done

`paidAmount` is written **only when the user supplies it**; skipping never
writes `0`. Validated as finite and non-negative, rounded to đồng (`1.6 → 2`),
and rejected for `""`, `null`, `NaN`, `Infinity`, negatives and `1e30`.
`purchasedAt` is an epoch ms; `previousStatus` is one of the real non-purchased
statuses. **Item IDs are never changed** — `applyPurchase`, undo, the chip and
the form all mutate in place and never regenerate an id (`P-15`, `U-04`,
`S6-03`). Legacy rows load untouched with no invented fields (`M-04`, `M-08`,
`U-10`). `normalizeItem()` strips purchase fields from any row that is not
`purchased`, so an inconsistent import cannot resurrect an undone purchase
(`M-09`, `S6-07`). Import and export preserve every valid field and drop every
invalid one (`S6-01`→`S6-09`).

**Every write path was checked, not assumed:**

1. `save()` → `writeItems()` → `setDoc({ ...item, id, image })` — the item is
   spread, so the new fields travel; proven by capturing the actual `syncItems`
   payload (`P-39`, `P-40`, `S5-05`, `U-21`).
2. `writeList()` → `localStorage` — `JSON.stringify(items)` includes them;
   proven by the round-trip and reload checks (`S6-03`, `S5-08`).
3. `importJson()` → `normalizeItem()` per row — proven hostile-input-safe
   (`S6-06`→`S6-09`).
4. `onRemoteItems()` read/merge — remote wins for shared ids, local-only ids are
   added (`S5-06`→`S5-10`, `U-23`).

### §2 Purchase capture — done

The dialog shows the **product name and the expected price**, offers an optional
actual price and a purchase date (defaulting to today), and has exactly the
three required actions. **Hủy changes nothing** — asserted for both the button
and `Escape` (`P-07`, `P-09`). Skipping the price stores no `paidAmount`, so the
item is owned but excluded from recorded spending (`P-21`, `P-22`). Success
feedback is a real toast **with a real action button** (`P-17`, `P-20`). The
card and Quick View buttons read **Hoàn tác** once the item is owned (`P-19`,
`P-29`).

The dialog is a **second, separate `<dialog>`** that opens *on top of* the Quick
View rather than inside it, so the user keeps their context — and because it is
the top layer, the toast host had to be fixed (§1.2).

### §3 Correct undo — done

Undo restores the **exact** recorded status; the legacy fallback is documented
in code and tested on its own. It clears `paidAmount`, `purchasedAt` and
`previousStatus` **for that one transaction** and touches nothing else: image,
note, expected price, category, priority, link and `createdAt` all survive
(`U-04`, `U-10`). No other item is affected (`U-11`, `U-12`). Account Firestore
data is not deleted — the row is written back in its new state, not removed
(`S5-11`, `S5-12`). **Two-way sync cannot resurrect the purchase**: the upload is
a `setDoc` without merge, so the document is replaced and the fields are gone;
the last upload is inspected field by field (`U-21`, `S5-12`) and a server
snapshot echoing it keeps the item out of `purchased` (`U-23`).

### §4 Collection Quick Tabs — done

One `items` array, one extra predicate inside `visibleItems()` — no second list.
Purchasing while on **Chưa mua** removes the card and offers **Xem đã mua**;
purchasing while on **Tất cả** leaves the card exactly where it was and offers
**Hoàn tác** (`T-17`→`T-24`). Nothing auto-navigates: the tab changes only when
the user clicks it (`T-18`). Search, the advanced filters, sort, Gallery and
Focus all keep working and compose with the tab (`T-08`→`T-15`, `S6-10`,
`S6-11`). The tab is UI-only state and is never persisted (`T-25`), and "Xóa bộ
lọc" returns it to **Tất cả** (`T-13`).

**Dashboard Quick Actions: partially deferred.** F2 provides the single
navigation entry point, `setPurchaseTab(tab)`, which the tabs, the toast and the
empty-state action all already use (T-19, T-21, T-10). The Quick Actions control
itself does not exist yet, because §6 explicitly defers the Dashboard 2.0
components — including Quick Actions — to F3. This is **not** claimed as a pass;
it is listed as the first F3 item in §11.

### §5 Metrics kept separate — done

All five figures exist, are computed by one `computeMetrics()` over the whole
collection, and are never merged. `#dvActualSpent` sums **only valid
`paidAmount`** and reads "Chưa ghi nhận" when there are none; `#dvUnpriced`
counts owned items with no recorded price; `#dvProgressValue` is ownership by
item count. `ownedValue` keeps its own label with its own disclaimer ("chưa phải
chi tiêu thực tế"). Every KPI is independent of search, filters and the quick
tabs (`D-07`, `D-08`, `D-09`) and updates the instant a purchase or an undo
lands (`D-10`→`D-13`). No `NaN` can reach the DOM, including from a corrupt
import (`D-14`, `S6-09`, `M-20`, `M-24`).

### §6 UI/UX — done

Design-token only: `css/purchase-v16.css` and the new `dashboard-v16.css` rules
reference `--dv-*` (which alias `--dream-*` from
`dreamscape-v5-tokens.css`) — no new palette, no reference-theme dark purple.
Desktop-first, and nothing overflows at **320, 390 or 430 px** (`S6-20`→`S6-22`);
the capture dialog and all three of its buttons fit inside a 320 px viewport
(`S6-23`). Buttons carry real disabled, `aria-busy` and `aria-invalid` states
(`P-05`, `P-11`, `P-13`). The dialog is semantic (`<dialog>` + `showModal()`),
returns focus to the button that opened it, keeps `Escape` as cancel, and blocks
`Escape` while a write is in flight (`P-06`, `P-08`, `P-09`). Quick View, card
tilt, scroll reveal and the Navigation Pill are intact — the motion suites are
green (M2 31/31, M4 28/28) and `prefers-reduced-motion` is honoured by the new
`transition` rules, which are wrapped in a reduce-media query.

**Dashboard 2.0 was deliberately not built.** No Status Distribution, no
Category Breakdown, no Priority Widget, no Quick Actions — those are F3.

### §7 QA gate — done

See §3.1 for the item-by-item mapping. Every listed case was actually executed.

## 11. Decision

# GO — for F3, on the existing branch

**Justification, in the order that matters:**

1. **168 / 168** F2 checks pass, and all **262** regression checks across the F1
   and V16 suites still pass. The only F1 changes were the three steps whose
   interaction contract F2 deliberately replaced; one of them (`CRUD-04`) now
   asserts the F2 fix.
2. **The data model is safe.** New fields are additive, validated, never
   invented, never coerced to `0`, and never written onto an item that is not
   purchased. Legacy rows load untouched. Item IDs are never regenerated.
3. **Undo is correct and reversible.** It restores the recorded status, clears
   only that transaction, and cannot be undone by a later sync snapshot.
4. **The hosting gate is green** with a smaller published surface than the old
   config — 54 files and **zero** leaked repo internals, against 842 files with
   723 leaks before the allowlist.
5. **No measurable regression.** Desktop performance flat, mobile within noise,
   accessibility up one point, CLS still 0.

**Conditions attached to the GO:**

* The GO is for **continuing on `feature/motion-auth-reset` into F3**, not for
  merging or deploying. `develop`/`main` stay untouched.
* Two-device sync (F2-N3) remains unverified and must be run on a real device
  before any Production release.
* The F2 work is not yet pushed; the push happens with this report.
