# Dream Vault V16.1 - F6 Motion Polish & Performance Recovery

Branch `feature/motion-auth-reset`, PR #1 -> `develop`. Baseline F5 HEAD
`4852b13`. Budget $0. **No Production action of any kind was taken**: nothing
was merged, nothing was tagged, nothing was deployed, `ui-v16.0.0 -> 562a62f` was
not moved, and the Firestore rules and the Cloudflare Worker were not touched.

F6 is not a redesign and adds no feature or widget. It is the milestone that
makes the app **cheap to serve** and **honest about motion**: the 52 render-
blocking stylesheets become one, the render cost and the long-task count were
measured instead of asserted, and every animation was checked for the four things
that actually go wrong (layout shift, stacking, wasted work, and missing
reduced-motion support).

| --- | --- | --- | --- | --- | --- | --- | --- |

| gzip | mobile | 93, 93, 93 | 2569, 2582, 2586 | 0 | 0 ms | 162 KB | 53 |

a11y 100, best-practices 100, SEO 100 in all 24 runs. The spread inside a cell
is 0-6 ms on LCP and 0 points on perf, so any F6 delta smaller than that is noise.

### 1.5 Diagnosis

1. **The payload is the problem, not the render.** 52 render-blocking requests
   and 561 KB raw / 162 KB gzip on the critical path, against a render cost of
   0.28 ms/item and one long task.
2. **The runtime is already healthy.** One observer, 12 listeners per card, zero
   `animate()` at load, CLS 0.002, TBT 0 ms. No listener leak, no animation leak.
3. **The one lever that is both safe and large is build-time CSS concatenation**:
   -28 299 gzip bytes and -51 requests, with no source change and no cascade
   risk (0 `url()`, 0 `@import`).
4. Everything else in the F6.2 priority list is either not a problem
   (`updateCategoryFilter`, duplicate selectors) or is explicitly out of scope
   (minify that could break semantics, risky refactors).

**Conclusion for F6.2:** do the build-time concatenation, prove equivalence by
running the full F1-F5 suites against `dist`, and do not touch the source CSS.

## 2. F6.2 - Safe payload & render optimisation

### 2.1 What changed

`scripts/build-hosting.mjs` reads the stylesheet order from the `<link>` tags in
`wishlist.html` (never hard-coded, so a sheet added or reordered in source can
never be silently dropped), writes `dist/css/app.css` as that exact
concatenation with one banner comment per source sheet, and rewrites
`dist/wishlist.html` to reference `css/app.css`.

`scripts/check-hosting.mjs` now carries a **byte-exact** invariant instead of a
file count: `dist/css/app.css` must be byte-identical to the concatenation of
every repo stylesheet in link order, no other CSS may be published, and the
published HTML must link `app.css` and no source sheet. The allowlist is
unchanged (`wishlist.html`, `wishlist-cloud.js` + generated `css/app.css`).

The source tree keeps its 52 separately-maintainable files. The change is
entirely in the build.

M3 32, M4 28) were run against `dist` with `npm run qa` and all pass. The
concatenation is functionally identical to the 52 separate sheets.

## 3. F6.3 - Dashboard motion polish

### 3.1 The genuine gap found

Three dashboard widgets (status distribution, category breakdown, priority) mixed
the **active filter value** into their change signature, so changing a filter
re-rendered and re-animated them even when the underlying data had not changed.
That is exactly the "replay the whole dashboard after every search/filter" anti-
pattern the spec forbids, and it showed up in the F6 motion suite as one extra
fade per filter change.

### 3.2 The fix

The active marker is now tracked **separately** from the data signature:

- `dvDistSignature` / `dvBreakdownSignature` / `dvPrioritySignature` hold the
  data only (counts, totals, buckets, stats).
- `dvDistActive` / `dvBreakdownActive` / `dvPriorityActive` hold the last active
  filter value.
- The widget returns early only when **both** are unchanged.
- A filter change still re-renders (so `aria-pressed` on the legend buttons
  stays truthful) but does **not** replay the fade.
- The fade runs only when the data signature actually changed.

The savings overview, the insights list, the KPI band and the quick actions
already guarded on data signatures and are untouched. No new state beyond three
strings, no new token, no new duration, no new animation.

### 3.3 Motion-correctness matrix (F6 suite section A)

| Check | Result |
| --- | --- |
| A changed KPI nudges; an unchanged one does not | PASS |
| The KPI nudge uses transform/opacity only | PASS |
| No nudge on the first paint | PASS |
| The ownership progress bar animates width via a CSS transition | PASS |
| The savings overview fades once on a real data change | PASS |

Cross-checks:

## 6. F6.6 - Reproducible QA

The F1-F6 functional suites, the V16 regression suite, the M1-M4 checks, the
syntax gate, the payload reporter and the interaction audit now live under
`scripts/qa/` instead of a developer's temp directory. Nothing in them reads
`C:\\Users\\Admin` or `E:\\Buying Checklist` any more: `ROOT` defaults to the
repository root, output goes to `qa-out/`, and `CHROME` is overridable through
an environment variable.

    npm install
    npm run qa

`npm run qa` runs all 12 suites sequentially (so the ports never collide) and
generates the F3 baseline tree from git (`93ef2c1`) if it is missing, so the F4
listener A/B runs the full 65 checks. Result on this tree: **759 checks,
0 FAIL**. Individual suites are available as `npm run qa:f1` .. `qa:f6`.

`scripts/qa/README.md` documents the dependencies, the run command, and what is
deliberately NOT tested (real Firebase, real Google sign-in, iOS).

`docs/qa/dream-vault-v16/f6-baseline.json`, `f6-render-baseline.json` and the
Lighthouse JSONs in `v16_6-out/` are the raw measurements behind sections 1 and
2.3. The ad-hoc measurement harnesses (Lighthouse, render baseline, audit
probes, screenshot runners) stay in the QA directory: they are diagnostics, they
write reports and screenshots, and several of them serve the app from a fixed
port.

### New in F6

  baseline probe measured 37 ms. Both are inside any reasonable budget and the
  F4.6 gate (45 ms against a 46 ms live baseline, budget 67 ms) still passes;

- **F6-N3** - the F4.6 render gate's measurement was made deterministic in
  `scripts/qa/f4-check.js`: it now times one explicit `render()` after the page
  has settled instead of taking the worst value from the load-time `__renders`

  (55 ms) is unchanged; only the measurement became honest. This is a
  methodology fix, not a weakened test.
- **F6-N4** - the F4 suite reports 62 checks by default and 65 with
  `--baseline=<tree>`. `npm run qa` generates the baseline tree from git
  (`93ef2c1`) automatically, so the full 65 run there.

## 9. Decision

**GO for F7 (Final QA & Production Readiness)**, on this branch, with no
Production action.

Why:

1. F6.1 - F6.6 are implemented. The F6 gate is **28 / 28**, and the full
   `npm run qa` battery is **759 / 759** with zero harness edits to make a red
   test green.
2. The one real finding (three dashboard widgets re-animating on a filter
   change) is fixed and verified; the fix is three strings and a fade guard.
3. The payload win is large and safe: -28 KB gzip, -51 requests, 0 new
   dependencies, 0 source CSS changes, and the cascade is byte-equivalent.
4. Lighthouse moved up on every cell: desktop 58 -> 63 (raw) / 71 -> 89 (gzip),
   mobile 71 -> 84 (raw) / 93 -> 100 (gzip), LCP down 25-45 %, a11y/BP/SEO 100,
   CLS 0.
5. Reproducibility is solved: one command, documented dependencies, no
   hard-coded paths, no secrets, no user data.
6. Nothing in F6 touched the data model, the Firestore rules, the Cloudinary
   Worker, the auth flow, or `ui-v16.0.0`.

Conditions carried into F7:

- Re-run `npm run qa` and the Lighthouse pair after any further change.
- Treat the payload budget as a first-class constraint (F6.2 already proved the
  win; F7 must not regress it).
- Keep `image/After Shave.webp` untracked and unstaged.
- No tag, no merge, no deploy.
